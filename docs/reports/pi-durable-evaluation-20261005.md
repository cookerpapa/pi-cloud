# Pi Durable 1.0: commit and remote Tool verification

Evaluation under [ADR-0228](../adr/0228-pi-durable-evaluation.md), starting from
`fe8226dd`. Production remains on Pi 0.84.1; no deployment or application schema
was changed. The isolated package pins Pi Durable, pi-ai and Chord to 1.0.0.

## Result

The two integration seams are usable: a durable Session can return at the existing
Kafka replication boundary, and its Tool intent can route a whole fixed Tool to
the deployed Cube executor and receive the original boot-scoped Kafka reply.
Pi Durable is not yet a replacement for CloudAgentRuntime under the current
contracts. Native abort settlement, UNKNOWN recovery and human queue policy
need explicit adaptation. Storage/protocol migration is substantial, not an
import-path update.

No upstream code was patched. The adapter uses public `MemoryStorage.prepareCommit`,
Harness, Tool hooks, task checkpoints and the Models port. It never runs a second
scheduler alongside Harness for the same task. Production does not import the
experiment. Source and reproduction commands are in
[the isolated fixture](../../scripts/experiments/pi-durable/README.md).

## What was executed

- [Storage conformance](pi-durable-conformance-20261005.json): all 23 upstream
  storage cases passed on the prepare/publish/apply adapter with an immediate
  publication stub. This validates adapter ownership/atomicity semantics; the
  separate transport probes below establish actual Kafka/PG behavior.
- [RF3 Kafka and PostgreSQL probes](pi-durable-verification-20261005.json): 15
  scenarios completed, including actual SIGKILL of three owned Node children.
  Five scenarios deliberately record incompatible behavior, representing three
  policy groups; `verified: true` does not mean `compatible: true`.
- [Actual Cube execution](pi-durable-cube-verification-20261005.json): a disposable
  VM executes the fixed Bash once, its final result reaches Pi Durable, and a
  later command receives ordered cancellation through the same private Session
  path. The original cancellation reply arrives, but Durable does not preserve
  its final content. The exact allocation is closed and recorded-node absence
  is confirmed.
- [Output and sampling policy](pi-durable-output-20261005.json): measures durable
  progress commits, reproduces the fail-open beforeRequest-hook behavior, and
  verifies a model-port guard instead.

Model responses are generated by upstream's scripted faux provider to make the
failure order and provider request counts deterministic. This is not a GPT-6
Luna/provider compatibility or token-usage test. Real Cube, its installed Guest
protocol 3/native protocol 7, and its existing Kafka completion code are exercised.

## Storage boundary

One fixture partition owner hosts the existing publication ingress and ordered
consumer. The adapter prepares and detaches a batch without exposing it, writes
one private envelope through the transactional RF3 writer, then calls `apply()`
after confirmation. PG asynchronously projects the exact batch. Handoff commands
are attached to the Tool intent batch, and the consumer confirms its dispatch
commit before requesting a physical effect.

| Contract | Observed result |
| --- | --- |
| Visibility before ACK | No publication callback or committed view is visible before confirmation. |
| PG projection lag | Hot commit resolves while the PG fixture still has zero rows; projection catches up afterward. |
| Duplicate projection | An identical batch is inert; changed bytes at the same position fail. |
| Proved pre-admission refusal | An oversized batch enters neither Kafka nor PG. Mapping `PublicationNotSentError` to `StorageRejected` keeps the Session usable. |
| Ambiguous publication | Kafka/PG may contain the batch, while the old Session is poisoned and exposes no unconfirmed commit. Reopen recovers the committed batch. |
| Ordered closure | The real ingress rejects subsequent writes after its writer seal. This uses a fixture grant, not full PG lease takeover. |
| Identity and effects | One saved operation ID identifies the callback and handoff. A normal Tool executes once and its result reaches the next model request. |

The PG fixture journal and private envelope are not the production Session
schema. Bootstrap here replays the small complete fixture journal. The production
requirements for latest Compaction/active suffix, indexed reads, fork deletion,
current documents/tasks, retention and attachment reachability remain work for
a real Storage adapter. There is no claimed lifetime-history or fleet benchmark.

## Confirmed semantic differences

### Stop can replace an uncommitted final remote result

After `Conversation.abort()`, upstream's Tool abort handler reconstructs a
result from the persisted live slot and adds `aborted`. It does not adopt the
remote callback's later final result, even when the callback confirms success or
`not_started`. The deterministic three-case matrix reproduces this, and the real
Cube cancellation also receives the original reply without retaining its partial
final content. Already committed Tool results are a different case.

This conflicts with ADR-0221/0227: ask the original operation to cancel, await its
bounded final reply, preserve known outcomes, and use UNKNOWN only when unconfirmed.
Do not solve it by relabeling a confirmed result, ignoring cancellation, or killing
the entire VM. An adoption proposal must define an upstream supported finalization
hook or a cloud Stop adapter that interrupts sampling while allowing original
Tool settlement. Neither solution is implemented or claimed by this evaluation.

### A throwing beforeRequest hook is not a sampling gate

The initial mixed-result assertion failed: with one UNKNOWN Tool and one ordinary
completed Tool, throwing from `beforeRequest` still allowed request two. Upstream
reports hook failures and continues. A single Tool's `control.terminate` had hidden
this because a one-Tool round satisfied the all-terminate condition.

The final probe preserves that finding and separately supplies a public Models
facade that refuses `streamSimple` before reaching the provider. In the same mixed
round the model receives exactly one request. PiCloud's authority, model permit and
UNKNOWN checks therefore belong at this existing host boundary, not in a hook
whose exceptions are observations. Persisted recovery gating still needs the PG
Run/lease mapping; a boot-local boolean is not that mapping.

### Restart and input policy differ

SIGKILL after an unsafe Tool intent does not re-execute it: the external fixture
counter stays one. Durable emits `interrupted` and resumes model sampling. An
explicitly replay-safe Tool executes twice; an already committed completed result
survives SIGKILL before its ACK without another execution.

PiCloud instead requires retiring/sealing the old Run, preserves UNKNOWN and does
not automatically resume its sampling under another Worker. Decide how a newly
PG-authorized Run may resume native tasks before enabling `Harness.resume()`.
The experiment is not permission to replay arbitrary shell effects.

Native queued submissions survive storage and can be individually withdrawn, but
`abort()` withdraws pending human inputs as `unanswered`. PiCloud pauses its PG
queue and waits for explicit Send/Continue queue. Keeping the product queue in PG
and admitting only the active work to Durable is a candidate, not a verified
replacement for current edit/reorder/promote and sealed-Steer reconciliation.

### Durable observations change the write workload

An eight-chunk Tool preview probe produces 23 total commits, eight containing the
preview, even though the final Tool result contains only `FINAL_ONLY`. The report
records exact encoded batch bytes. These counts describe the entire small fixture,
including setup/model/task state, not an invariant per Tool or a throughput claim.
Native `api.output()` is therefore not the replacement for PiCloud's lossy HTTP/SSE
preview path. The remote bridge can keep previews outside it. Model partials and
native task/document transitions also require a PG write-amplification assessment.

## What could become smaller

| Current component | Candidate role with Durable |
| --- | --- |
| `sandbox-supervisor/cloud-agent-runtime.ts` | Upstream generation, retry, compaction and task mechanics could replace parts of the orchestration. Cloud sampling policy and Run authority remain. |
| `pi-session-postgres` and native writer | New Storage/record projection is needed; public prepare/apply can serve the live view. Existing v4 Entry/Lane types do not map by renaming imports. |
| Queues and Subagents | Native inbox and task ownership can supply in-process mechanisms. PG admission, public queue behavior and cross-Run coordination need their own mapping. |
| Ingress and Session Projector | Retain ordered publication, fencing, projection and dispatch-before-effect; teach them an explicitly chosen new native batch schema. |
| Cube, completion and reply mailbox | The current whole-Tool transport can remain behind an adapter, as the real fixture demonstrates. |

No deletion percentage is claimed. This evaluation did not migrate the complete
Worker or measure a reduced production codebase.

## Scope and cleanup

The fixture uses local, synthetic authorization grants. It does not exercise the
production publication HTTP routing, PG Run claims/takeover, Subagent protocol,
frozen environment snapshots, image read/claim-check, hosted tools, compaction
recovery or long-history bootstrap. The live test uses the current deployed guest
Tools behind the PiCloud-owned reply schema, not Durable's image-incomplete built-ins.

The first host-only live attempt failed at Kafka topic setup because advertised
Service names were not resolvable; no Cube creation was attempted. The successful
rerun uses container-local aliases in a temporary trusted probe container and the
same deployed image by digest. Host/cluster DNS and application deployment were
not changed. The failed mixed-hook assertion was a real compatibility finding;
both attempts remain in the private diagnostic logs, not counted as green runs.

[Final inventory](pi-durable-inventory-20261005.json) confirms no private probe
topics, no owned reply topic, zero VMs on the recorded node, and all running Pods
ready. The remaining reply topics belong to the existing Worker service. The
disposable PG and RF3 Kafka fixtures report successful cleanup. No application
conversation, Workspace, image object or historical UNKNOWN allocation was reset.
