# ADR-0284：独立 Fork、共享历史正文与安全回收（修订提案）

状态：**已获准实施，S0 存储验证待完成，尚未上线**。2026-10-28。
用户在方案修订后要求与主分支整理、首请求延迟对比一并实施。
实施仍须通过下文 S0–S4 门槛；不把未通过的存储验证视为已经完成，
不以此执行一次用户会话或 Workspace 数据清空。

## 要交付的行为

原会话为 `A → B → C → D → E`，在 C 创建手动 Fork，Fork 继续生成 F。

- 原会话正在处理 D/E 时，可以从已经完成并投影到 PG 的 C 分叉。
- Fork 正在运行时，已收尾的原会话可以裁剪到 B。
- 原会话变成 AB；Fork 保留 ABCF，执行租约和 Worker 不因原会话裁剪而变化。
- 公共历史正文 ABC 只保留一份共享内容，各会话有自己的记录身份和引用。
- D/E 在没有任何保留者后最终回收；C 仍被 Fork 引用时不能回收。
- 刷新、分页、搜索、导出、再次分叉、压缩和 Worker 恢复使用同一套历史归属。

这里的独立 Fork 是用户手动创建的独立会话。原任务派生的 Subagent
仍属于其物理 Session 执行家族，继续遵守原有收尾和 fencing 规则。
Workspace 文件仍按现有绑定管理；裁剪会话不是文件回滚或 Workspace 克隆。
“删除后续”不能隐式执行整树删除。现有明确选择的整树删除属于另一个操作范围，
其确认文案和入口必须与单会话裁剪区分。

## 已核对的事实

1. 当前 `copyDurableHistory` 为独立物理 Session 复制 Entry 和应继承的文档。
   图片字节复用对象存储，文本和工具结果正文确实重复。
2. `ConversationReader`、`canonical-history-window` 和导航树仍沿父会话查轮次、
   分叉点和部分工具信息。只删除级联裁剪条件，会留下读取依赖。
3. 当前裁剪把后续 Run/分支标为 `pruned_at`，通过原生 Conversation 分叉切换视图；
   不会逐条物理删除原生日志。完整物理 Session 删除才级联清除该日志。
4. `rebuild()` 要求提交序号连续，并核对每批历史条数及摘要。
   直接删除日志中间几条正文会被当作损坏，不能作为 GC 实现。
5. Pi Durable 1.0 的原生分叉在同一个 Storage/物理 Session 内记录祖先和截止 Entry。
   它共享祖先 Entry，并按 `asOf`/`current` 规则处理文档；并未提供跨独立 Storage
   的共享历史对象或可直接调用的历史节点 GC 接口。

固定依赖为 `@earendil-works/pi-durable@1.0.0`，MIT，npm gitHead
`a13d35a742c6ef8462812a28fbe1d8c8b7431c32`。
本地使用其公开 Session/MemoryStorage 做了 ABCDE 实验：从 C 分叉只新增 Conversation，
Fork 可见 ABC；另建截止 B 的视图后，Fork 仍可见 ABCF，但旧 Storage 中 DE 仍存在。
另一份 Storage 不会自动拥有 C。实验没有启动 Agent Harness、模型或工具。
这证明原生共享的范围，不证明下面的 PG 适配已经完成。

对一个现有长会话做的匿名只读抽样：434 个 Entry，正文约 **3.39 MiB**；
全部原生日志正文约 **4.50 MiB**；43 个保留图片对象约 **115.25 MiB**。
当时没有存活的用户手动 Fork。统计是 UTF-8/对象原始字节，不含索引、WAL、
TOAST 压缩和 Kafka 副本，也不是容量或延迟基准。当前节省空间的绝对收益有限；
共享正文的主要动机是明确分支长期存储和回收语义，不能宣传成已测得的性能提升。

私有证据：`deploy/production/runtime/research-evidence/independent-fork-20261028/`。
不提交用户会话正文、图片或凭据。

## 采用已有能力的比较

| 候选 | 证据与适用边界 | 选择 |
|---|---|---|
| Pi Durable 1.0 原生 Conversation fork，MIT | 固定源码和本地实验；同一 Storage 的祖先引用、文档分叉策略 | 保持其语义和公开 Storage 接口。用户独立 Fork 不因此合并执行租约或 Worker 归属 |
| PostgreSQL 现有部署 | 事务、外键、唯一约束、MVCC 快照；可把引用建立与业务提交放在同一权威数据库 | 采用这些原语实现有界存储适配，不增加服务或计数权威 |
| Git，调查时最新标签 v2.56.0，GPLv2 | 不可变对象、引用和回收；官方明确说明并发写入与 prune 的风险 | 借鉴先保留引用再回收的原则；不把 Git 仓库引入 PG/Kafka 提交边界 |
| lakeFS v1.88.0（2026-10-01 发布） | 对象版本、分支及 GC；当前主仓库声明 BUSL-1.1，不能称为无条件开源依赖；GC 文档列出 shallow-copy 与 mark/sweep 的竞态 | 调查其失败语义，不引入额外对象目录服务和 GC 作业栈 |

选择 PG 的原因是：引用、会话准入和冷态切换能够使用已有事务边界。
引入 Git/lakeFS 仍需协调另一套引用权威与 PG/Kafka，无法替代 Pi 的恢复合同。
拟新增的只是 PiCloud Storage 适配层的正文解析、引用和冷态重整代码；
不建立通用版本数据库、通用 DAG 调度器或一套自维护的内存引用计数系统。

## 推荐设计：共享正文，各 Session 独立持有记录

共享的单位是不可变 Entry 正文，不是执行中的 Task，也不是一个可变的父会话。
继续保留一物理 Session 一 writer、一租约、一套 seq 和独立恢复边界。
每个独立 Fork 仍可由不同 Worker 运行。Subagent 的物理 Session 规则不变。

拟在 PG 增加一个租户内的不可变正文对象关系；现有原生日志的 Entry 行保存引用和
该 Session 内的身份信息。具体 DDL 在存储验证通过后固定，逻辑形态为：

```text
正文对象：租户、对象 ID、编码版本、正文 TEXT、完整性摘要
Entry 记录：所属物理 Session、seq/ordinal、Entry ID、Conversation ID、
            原生来源字段、正文对象 ID、不可变的展示来源信息
```

- 同一次历史分叉直接复用已知对象 ID，不做全库相同文本去重，也不跨租户共享。
  对象 ID 永不复用；摘要用于完整性检查，不单独充当引用或权限证明。
- 正文与 Session 内身份分离，适配层重建 Pi 要求的完整 Entry。
  Fork 的 `byTaskId` 等执行来源沿用现有独立拷贝规则，不能指向另一 Session 的活任务。
  Entry 的 `head`、ContextEdit 引用及其他内部 ID 必须保持一致。
- 原生文档继续按 `asOf`/`current` 复制独立状态；`initial`、Task、Session 运行状态
  和待处理输入不因手动 Fork 获得执行权。不能把可变文档强行共享。
- 正文只存一处。不能在对象表和原 `body` 列同时保存一份完整 Entry；其他记录种类
  保持原生存储政策。SQL 读取在分页边界内 join 对象，避免每条消息单独查一次。
- Kafka 仍接收 Worker 的完整原生提交，R=3 ACK 语义不变。这是 PG 表示变化；
  不在 `Storage.commit()` 中删字段，也不把 Kafka 改为终身共享正文仓库。
- 原批次 fingerprint 保留原义。PG 重建验证需要明确的新表示摘要和条数规则；
  原生 JSON 的 NUL、孤立代理项及附件引用必须可无损恢复，不能强转成 JSONB。

Fork 仍需创建 O(历史记录数) 的轻量引用/索引，故不能称为 O(1) 零成本分叉。
减少的是重复正文。新索引行、独立文档基线和必要展示元数据仍占空间。

## 分叉与读取

固定 PG 中已完成、已投影的截止点，读取一个一致的源快照。配额、幂等、目标创建和
删除并发保护仍由写事务承担，不能仅因使用 Repeatable Read 就取消这些检查。
多批引用建立、文档种子、图片保留和创建收据必须全部成功才返回成功。
并发操作要么得到完整 Fork，要么明确失败；不能返回缺失正文或图片的会话。

正文对象引用和图片引用在提交前建立。使用实际 FK/引用行及必要行锁保护正在复制的
对象；读快照本身不是对象存储保留证明。复制中断则回滚未提交的目标，重试沿用幂等键。

Fork 的历史分页、工具展示、导航、搜索、导出和上下文读取改为自身的存储范围。
已执行输入的展示信息、轮次终态及工具对应关系需要随历史固定；不创建可领取的历史 Run，
不把当前 Inbox 变成历史队列。原会话 ID 只表示来源，不能作为读取副本的必需连接。
源节点被裁剪后，来源标记仍可展示，Fork 自己的 C 仍可定位。

## 裁剪与物理回收是两个明确阶段

**裁剪阶段**只修改当前会话的保留边界，手动 Fork 不参与级联删除或运行状态检查。
当前物理执行家族必须已收尾；存在未关闭 writer、恢复后缀或活跃 Subagent 时，
仍不能进行冷态原生状态变更。前端按这些条件置灰并说明原因。

**清理阶段**不得从仍受校验的 append-only 批次中直接挖掉 DE。
推荐验证以下冷态重整路径，作为实现前的必过门槛：

1. 在已有准入保护下确认原物理 Session 无 writer，已封口并投影完成。
   冻结需要保留的产品视图、原生 Conversation 祖先范围、文档基线、图片引用及恢复约束。
2. 使用公开 Storage 合同初始化一份新的物理 Session 存储，只保留仍需要的历史引用和
   合法状态。正文对象复用；新存储有自己的正常 seq、完整校验和 ID 水位。
   这是冷态历史整理，不是给活跃 Run 增加 attempt，也不是复制一个运行中的 Agent。
3. 验证新存储的上下文、可见历史、文档策略和重建结果。多 Lane 家族必须整体验证；
   不能只整理主 Conversation 就删除子 Agent 仍依赖的祖先。
4. 在一个 PG 事务中校验源绑定/状态未变化，切换相应产品 Session 的现有
   `pi_session_id`/Conversation 绑定和读视图版本。旧、新存储不能同时成为有效 writer。
   用户可见的 Session ID 保持不变，独立手动 Fork 的绑定和租约不参与切换。
5. 旧存储在确认无产品引用、无 writer、无在途操作/恢复保留后，走现有物理 Session
   删除边界退休。需要重试的清理意图沿用现有控制 Outbox，不新增工作流系统。
   切换前崩溃保留旧状态；切换后崩溃从已提交绑定继续，绝不猜测应该删哪份。

未消费输入、未取回的 Stop 返回内容、导出/读取保留和子 Agent 发现所需数据不能丢。
实现验证必须明确哪些状态可迁移，哪些会推迟清理；无法证明安全时保持引用并报告原因。
本提案尚未证明复杂家族冷态重整可用。若公开 API 无法保持这些合同，停止该路径、
提交新的设计结论；不能偷偷修改 Pi core 或把仅隐藏历史宣布为完成回收。

历史游标必须带有对应读视图版本；重整后旧游标不能误指向新的 seq。
可重新定位保留 Entry 的游标才可恢复，否则明确刷新历史窗口。

## 对象回收的安全条件

当前例子在旧存储安全退休后的引用关系为：

| 正文 | 原会话 AB | 运行中的 Fork ABCF | 回收条件 |
|---|---|---|---|
| A、B | 有引用 | 有引用 | 保留 |
| C | 无引用 | 有引用 | 保留 |
| D、E | 无引用 | 无引用 | 无其他保留者后可回收 |
| F | 无引用 | 有引用 | 保留 |

以实际存储引用行作为权威，不手工维护 `ref_count++/--` 的第二本账。
每条正文引用使用租户内外键；对象删除采用有界候选扫描、事务内重新检查和 FK 约束。
并发新增引用与删除必须串行地得到“建立引用成功”或“对象不可用、操作失败”，
不能出现已确认的悬空引用。候选扫描得到的零引用结果不能直接用于事务外删除。

根集合包括已发布 Session、尚未切换完的存储、被保留的原生文档/祖先范围、
在途 Fork/读取及恢复所需状态。冷态重整之前保留旧引用属于安全保留，不能统计成已释放。
Kafka 的未投影提交和恢复后缀继续受现有保留边界保护；其原生消息仍携带完整写入，
新正文对象和 PG 引用一起提交。旧 Session 的 Kafka 重放不得复活已退休存储或已删内容。

图片继续使用现有 PG 引用 + S3 对象。新存储的图片引用必须先建立，才可移除旧引用；
同时保留上传 pin、未封口 Run 等保护。清理仍先关闭新引用准入、再删对象、成功后删元数据，
失败保留重试。Session 级保守引用在冷态重整时按保留状态重新建立，不按单条 UI 消息猜测。

“最终回收”以数据库和对象存储可用、保留者已释放、清理任务继续执行为前提；
不承诺点击后立刻释放磁盘文件。PG DELETE 的空间复用仍由 VACUUM 管理，Kafka 按现有
安全分区前缀清理。增加可观察的待清理数量、字节和阻塞原因，避免无声地永久保留。

## 验证与实施顺序

先完成一个隔离的 Storage 验证切片，再实现界面行为。上线前所有门槛必须通过。

| 阶段 | 必须证明的结果 |
|---|---|
| S0：存储可行性 | 原生 Storage conformance；共享正文解析与直接存储相同；ContextEdit/head/文档分叉策略正确；原批次去重校验不变；复杂家族冷态重整可恢复 |
| S1：独立读取 | 源会话裁剪后 Fork 的分页、工具记录、图片、搜索、导出、usage 和冷启动上下文一致；不回查父 Run 的可见性；无 N+1 正文查询 |
| S2：操作边界 | 原会话运行中从已完成 C 分叉；Fork 运行中原会话裁剪到 B；原家族自己的忙碌/封口检查仍有效；幂等重复返回同一结果 |
| S3：回收与故障 | Fork 与裁剪/GC 并发；复制、切换、清理各阶段崩溃；图片删除失败；源缺失；嵌套 Fork；Subagent 祖先依赖；旧 Kafka 重放均不误删、不复活 |
| S4：体量与发布 | 1 GiB 合成历史和多分支验证有界内存、分页查询及正文只存一次；量化元数据成本和冷态重整耗时；匹配发布后在隔离真实会话演练 |

物理回收验收必须查对象行/引用和实际对象存储，不能只检查页面上 DE 消失。
当前仅完成源码调查、体量抽样和原生同 Storage 分叉实验，S0–S4 尚未完成。

需要调整数据库表示、Storage 读写/重建、历史读取、裁剪与前端条件，属于匹配升级，
不能套用 ordinary-Tool 或 Web-only 发布。依赖版本保持固定；不新增基础设施组件。
既有数据需要一次性转换并验证，删除旧表示和旧联动路径，不保留双写/回查父历史的兼容分支。
生产原会话、图片、账号、模型配置和 Workspace 不作测试清理对象。

导出应解析引用，产生可独立恢复的原生记录和附件清单，不能要求恢复者拥有旧父会话。
回退使用匹配版本与验证过的逻辑导出/恢复，不能让旧二进制读取新的对象引用布局。
验收前保留必要的短期切换恢复材料；结束后按开发阶段政策清理，不长期维护第二份业务历史。
